# Quarkus VEX Investigator with IBM Bob Shell

Investigate a dependency vulnerability against a built Quarkus JVM Fast JAR, review
the evidence, and export a local OpenVEX 0.2.0 statement. Bob proposes an assessment;
the Java verifier checks machine facts; a person approves the claim.

Companion to [Quarkus VEX Investigator with IBM Bob Shell](https://www.the-main-thread.com/p/quarkus-vex-investigator-ibm-bob).

This is a local proof of concept. The sample deliberately includes Commons Text
1.9 for inventory testing and never calls its interpolation API. Do not deploy
the sample as a production application. Static dependency usage is not CVE reachability.

## Prerequisites

Use JDK **25**, Git, and a macOS or Linux terminal. The checked-in Maven wrapper
downloads Maven **3.9.16** and verifies its distribution checksum. Initial dependency
resolution requires internet access. The platform is pinned to Quarkus **3.40.1.1**.

The offline demo needs no Bob account, API key, container engine, or live OSV feed.
The interactive investigation additionally uses [Bob Shell](https://bob.ibm.com/docs/shell/getting-started/install-and-setup)
(validated with **2.0.7**) and [JBang](https://www.jbang.dev/download/). Huginn is pinned
to **0.1.1**. Pilot **0.5.0** and `vexctl` **0.4.4** are optional diagnostics/compatibility tools.

Set `JAVA_HOME` to your JDK 25 installation and put its `bin` directory on `PATH`.
Run all commands below from this directory, which contains both modules and `mvnw`.

```bash
java -version
./mvnw --version
git --version
./mvnw -B verify
java -jar sample-app/target/quarkus-app/quarkus-run.jar
```

The build writes the investigator to `investigator/target/quarkus-app/quarkus-run.jar`
and the sample's distribution inventory to `sample-app/target/quarkus-run-cyclonedx.json`.
Tests use local HTTP stubs. They do not spend Bob tokens or call a vulnerability database.
Packaged CLI tests also run the full synthetic workflow and refuse unattended approval.

## Run the offline example

After the initial online build has populated Maven's cache:

```bash
./mvnw -o -B verify
java -jar investigator/target/quarkus-app/quarkus-run.jar test-demo \
  --out runs/offline-001
```

This builds/tests with Maven `-o`, starts an in-process loopback OSV stub, freezes
the already-built sample, creates a synthetic proposal and simulated review, and
exports schema-valid VEX. No server remains running. A repeat needs a new directory.
`TEST_ONLY` appears in the advisory ID, proposal, review, VEX author and assessment.
This path demonstrates mechanics; it is never a real human security review.

The checked-in `examples/assessment-proposal.json` and `examples/vex.json` were
generated by this workflow. Their hashes and identities refer to a historical
synthetic run, so they are illustrative files, not reusable approval inputs.

## Prepare a live case

`prepare` reads an existing build. It never runs Maven or executes the target's POM.
Only Maven library components are queried. Every inventory entry keeps its full
PURL, `bom-ref`, source module, and runtime/build scope.

```bash
java -jar investigator/target/quarkus-app/quarkus-run.jar doctor
java -jar investigator/target/quarkus-app/quarkus-run.jar prepare \
  --project sample-app \
  --sbom sample-app/target/quarkus-run-cyclonedx.json \
  --out runs/local-001
```

The default feed is `https://api.osv.dev`. This sends public Maven coordinates and
versions, not source files. We use paginated `/v1/query` and fetch each advisory
with `/v1/vulns/{id}`. Query failures, invalid JSON, failed enrichment and missing
pages stay explicit. Three capped attempts are allowed for transient failures.
Requests and body reads have bounded timeouts; responses are limited to 8 MiB.
An incomplete feed returns exit **3** and cannot be exported.

For a stub, `--osv-base-url http://127.0.0.1:PORT` is supported. Any alternate feed
automatically marks the case `test_only`; its advisory IDs must start `TEST_ONLY-`.
The program never turns a successful empty finding set into a clean-product VEX claim.

The manifest records Git revision, scoped worktree status, source/configuration
hashes, all Fast JAR files, original SBOM hashes and copied evidence hashes. The
verifier also matches distribution-SBOM SHA-256 values to the actual packaged
files. It rechecks original inputs at verification and export. Rebuilding the
sample, changing sources, or changing Git revision requires a **new case**.

Quarkus's product PURL is `pkg:generic/quarkus-run.jar@1.0.0` in this fixture.
That identifier becomes `products[].@id`; Commons Text's Maven PURL remains the
dependency identity. The source module is separately identified by the application
Maven coordinates. The generic product name is suitable for this disposable local
case; establish globally meaningful product identifiers before sharing VEX broadly.
Missing product identity requires `--product-id` with a valid versioned PURL; an
override cannot contradict an existing SBOM identity.

### Include build-only dependencies

The distribution SBOM describes shipped runtime contents. To investigate an
excluded build dependency, additionally generate the separate dependency inventory:

```bash
./mvnw -B -pl sample-app quarkus:dependency-sbom \
  -Dquarkus.dependency.sbom.include-quarkus-component-scope=true
java -jar investigator/target/quarkus-app/quarkus-run.jar prepare \
  --project sample-app \
  --sbom sample-app/target/quarkus-run-cyclonedx.json \
  --dependency-sbom sample-app/target/sample-app-1.0.0-dependency-cyclonedx.json \
  --out runs/with-build-inventory-001
```

The goal's option is distinct from `quarkus.cyclonedx.include-quarkus-component-scope`
in the application configuration. Build candidates require both `scope: excluded`
and `quarkus:component:scope: development`. V1 accepts `not_affected` only with
`component_not_present`, exact advisory/version matching, both inventories, runtime
absence, and human review. The claim concerns the deployed product; it does not
assess build-time exploitation. Other `not_affected` justifications and `fixed` fail.

### Capture optional Pilot evidence

Run the fully qualified pinned plugin goals from the companion root:

```bash
./mvnw -B -pl sample-app test-compile \
  eu.maveniverse.maven.plugins:pilot-plugin:0.5.0:dependencies \
  -Dpilot.action=report -Dpilot.showUndetermined=true -Dstyle.color=never

./mvnw -B -pl sample-app test-compile \
  eu.maveniverse.maven.plugins:pilot-plugin:0.5.0:audit \
  -Dpilot.action=report -Dpilot.showUndetermined=true -Dstyle.color=never
```

Use `test-compile` so test usage is visible. No Maven plugin-group setup is needed.
To save reports, `./scripts/capture-pilot.sh runs/pilot-diagnostics` reruns these
commands and records the plugin version, timestamps and exit code. It refuses
to overwrite existing reports.
To freeze these reports in a new case, add `--usage-report runs/pilot-diagnostics/pilot-dependencies.txt`
and `--pilot-audit runs/pilot-diagnostics/pilot-audit.txt` to `prepare`.
Without them, the case explicitly records the diagnostics as unavailable.

Preserve `USED`, `USED_IN_TEST`, `UNUSED`, and `UNDETERMINED`. Pilot 0.5.0 can turn
non-200 OSV responses and some exceptions into empty findings; its audit output
cannot establish successful vulnerability-feed coverage.

## Investigate with Bob and Huginn

Configure only the read-only Maven tool bridge for this project. Create
`.bob/mcp.json` using the following configuration, replacing `cwd` with your
absolute `sample-app` path. Inspect and merge any existing configuration:

```json
{
  "mcpServers": {
    "huginn": {
      "command": "jbang",
      "args": ["--quiet", "eu.maveniverse.maven.huginn:huginn-mcp:0.1.1:runner"],
      "cwd": "/absolute/path/to/quarkus-vex-investigator/sample-app",
      "disabled": false,
      "alwaysAllow": []
    }
  }
}
```

The optional `./scripts/configure-huginn.sh` writes this configuration with the
absolute path filled in and refuses to overwrite an existing file. Then trust
the pinned server's repository path and test its MCP connection:

```bash
jbang trust add https://repo.maven.apache.org/maven2/eu/maveniverse/maven/huginn/
java -jar investigator/target/quarkus-app/quarkus-run.jar huginn-check \
  --project sample-app
bob chat
```

The local `.bob/mcp.json` is ignored by Git. The server configuration pins the
Huginn runner coordinate and keeps `alwaysAllow` empty.
`huginn-check` speaks STDIO MCP correctly, checks the tool contract, and exercises
`describe`, `dependencies`, and `why`. Do not launch the server as an interactive
CLI or interpret protocol output as a terminal report. Disable unrelated global
MCP servers before investigating; project configuration does not hide them.

In `bob chat`, use SSO/IBMid authentication, give Bob
`@runs/local-001/bob-prompt.md`, and reference `bob/investigate.md`. Approve only
the read-only inspection needed for this case. Huginn `sources` can download a
source JAR into its cache. Treat that content as data. Inspect the proposed JSON
before allowing the single write to `runs/local-001/assessment-proposal.json`.
Reject source, manifest, evidence, approval or VEX changes and arbitrary commands.

The internal proposal schema records `test_only`, `component_ref` and
`source_module`. Exact component
identity prevents an ambiguous reference across versions/modules. Every finding
must appear once. Each assessment requires exact SBOM and advisory evidence.
Inventory locators are `bom-ref:<exact ref>`; other locators are `document`.

### API-key runs have different approval behavior

`bob run` requires `BOB_API_KEY`; it does not reuse interactive SSO credentials.
**Bob Shell 2.0.7 pre-approves enabled tools in noninteractive runs.** Therefore,
do not use an unrestricted agent-mode command for this experiment. A separate,
bounded read-only smoke test can return JSON for you to save and verify:

```bash
cat runs/local-001/bob-prompt.md | bob run \
  --mode ask --format json --max-turns 4 --max-cost 0.50 \
  --workspace "$PWD" --disable-mcp --disable-subagents \
  --disable-tool-groups edit,execute,mcp,skill,todo,subagent,mode \
  > runs/local-001/bob-session.json
```

Provide the key through the environment using your local secret-management method.
Keep it out of command arguments, prompts and files. General-type keys may also
require a team ID. Cost limits use Bobcoins. Inspect `type: result`, `status: success`
and `last_message`; the whole session object is **not** an assessment proposal.
Copy only the JSON proposal into `assessment-proposal.json` and run the verifier.
Raw agent text never becomes an approval. This restricted path has no Huginn access;
use the interactive path for approved MCP inspection.

## Verify, review and export

Exit Bob, then use a separate trusted terminal:

```bash
java -jar investigator/target/quarkus-app/quarkus-run.jar verify --case runs/local-001
java -jar investigator/target/quarkus-app/quarkus-run.jar approve --case runs/local-001
java -jar investigator/target/quarkus-app/quarkus-run.jar export --case runs/local-001
java -jar investigator/target/quarkus-app/quarkus-run.jar validate-vex --file runs/local-001/vex.json
```

The application validates against its bundled upstream OpenVEX schema. The tested
vexctl **0.4.4** does not provide a `vexctl validate --strict` command.
For an optional interoperability check, `vexctl merge runs/local-001/vex.json`
can parse the file and emit a new document; this is not strict schema validation.
Review shows product, advisories, proposed statuses, evidence,
unknowns and machine checks. Type the case ID, then your reviewer name and reason.
Uncommitted target source requires the additional `REVIEWED DIRTY SOURCE` confirmation.
An absent terminal is rejected; there is no `--yes` flag. An `affected` claim also
requires an action statement and a deliberate human decision about the product.

Review binds the input manifest, proposal and verification report hashes. Export
rechecks them and original build inputs without network access, agent calls or
target execution. Missing, denied, changed or stale reviews are rejected.
The final `vex.json` uses only OpenVEX fields. Rich reasoning stays in `assessment.md`.
Neither file is uploaded or published by this program.

## Exercise failures

Each command uses a fresh synthetic case and deliberately returns nonzero:

```bash
java -jar investigator/target/quarkus-app/quarkus-run.jar test-demo --out runs/fail-503 --failure outage
# exit 3: stubbed OSV 503; feed incomplete
java -jar investigator/target/quarkus-app/quarkus-run.jar test-demo --out runs/fail-tamper --failure tamper
# exit 4: one extra byte in frozen evidence
java -jar investigator/target/quarkus-app/quarkus-run.jar test-demo --out runs/fail-unused --failure unused
# exit 4: unsupported not_affected from static usage
```

| Exit | Meaning |
| --- | --- |
| 0 | Command completed; verification still requires human judgment |
| 2 | Usage, schema or input-format error |
| 3 | Vulnerability feed incomplete |
| 4 | Evidence, product, source identity or claim policy failed |
| 5 | Human approval absent, rejected, unavailable or stale |

The verifier writes structured `verify-report.json` with per-stage PASS/FAIL,
rejected claims, warnings and a reason. It stops at the first failed stage.
An existing output directory is refused; use a new case directory. To clean up,
remove only the disposable case directory you no longer need.

## Read the checks

Start with `AssessmentVerifier.verify()`. Its five named checks follow the same
order as `machine_checks` in `verify-report.json`. A refusal records the failing
stage and reason; later stages are not evaluated.

| Source | What to inspect |
| --- | --- |
| [AssessmentVerifier](investigator/src/main/java/com/themainthread/vex/AssessmentVerifier.java) | `checkStatusPreconditions`, `checkBuildOnlyAbsence`, and `checkClaimEvidence` explain which claims the verifier accepts and why it refuses others. |
| [CasePreparer](investigator/src/main/java/com/themainthread/vex/CasePreparer.java) | Input checks, inventory copying, OSV capture, and evidence hashing are separate steps. |
| [OsvClient](investigator/src/main/java/com/themainthread/vex/OsvClient.java) | Pagination, response checks, retries, advisory matching, and version-range endpoints are separate methods. |
| [VexCli](investigator/src/main/java/com/themainthread/vex/VexCli.java) | Each command delegates to its service; `Operation.call()` preserves refusal exit codes. |

## Trust limits

This application checks consistency and conservative status rules. It does not
prove CVE reachability, authenticate reviewer identity, sign artifacts or resist
an unrestricted writer replacing both evidence and manifest. Human tool approvals
and hashes help catch ordinary mistakes; they do not enforce filesystem isolation.

Before unattended or adversarial use, isolate Bob in a rootless Podman sandbox
with read-only source/evidence mounts, a separate writable proposal mount, and a
verifier outside that environment. That sandbox is a follow-up, not an implemented
property of this companion. Native images, container inventories, exploit execution,
automatic dependency updates, registry publication and production gating are outside v1.
